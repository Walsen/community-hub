# Architecture

Community Hub provisions AWS Lightsail environments, deploys forum engines into them, and configures each forum from YAML metadata. Everything is TypeScript. The spec design (`.kiro/specs/lightsail-forum-platform/design.md`) holds the detail; this file holds the rules.

## Three layers, one source of truth

```
metadata/*.yaml ──► Metadata_Loader (parse + validate) ──► ValidatedModel
                                                            │
                         ┌──────────────────────────────────┴───────────────┐
                         ▼                                                  ▼
               CDK_App (infra + install)                          Seeder CLI (forum config)
               cdk deploy / destroy                               seed [--forum id] [--dry-run]
                         │                                                  │
                         ▼                                                  ▼
   Lightsail instances, static IPs, firewall, snapshots       Forum admin REST APIs
   Route 53 zone + records, SES identity + senders,           (Discourse, Flarum)
   IAM node roles, bootstrap broker, custom resources
```

- The Metadata_Loader is the only code that reads YAML. Both the CDK_App and the Seeder consume its `ValidatedModel`, never raw YAML.
- The CDK_App owns infrastructure and first-boot installation. It never calls forum APIs.
- The Seeder owns forum content and configuration. It never creates or mutates AWS infrastructure. It only reads secrets.

## Repository layout

```
bin/
  app.ts                 # CDK entry: load metadata, build one stack per Environment
  seed.ts                # Seeder CLI entry point
src/
  metadata/              # Zod schema, loader, cross-field + mail validation, bundle table, secret refs
  engines/
    engine-adapter.ts    # EngineAdapter interface (the plugin contract)
    registry.ts          # EngineRegistry + createDefaultRegistry() (only importer of concrete adapters)
    discourse/  flarum/  # install script, email refresh script, TLS capability, seed client
  infra/
    environment-stack.ts # the single stack per Environment
    forum-instance.ts    # L3: instance, static IP, firewall, node role, lifecycle, A record, SES sender
    dns/                 # Route 53 zone (create or validated lookup) and record factories
    email/               # SES identity, config set, SNS topic, per-forum sender, SMTP password derivation
    tls/                 # ACME challenge selection, Route 53 DNS-01 policy statements
    user-data/           # shared prelude, TLS (lego) script, pins, composition
    handlers/            # Lambda handlers: bootstrap broker, forum lifecycle, SES credentials, email refresh
    naming.ts            # deterministic resource naming
  seeder/                # desired.ts, reconciler.ts (pure), executor.ts, report.ts, run.ts
  shared/                # secrets.ts, logger.ts (redaction), http.ts, errors.ts
metadata/example.yaml
test/                    # mirrors src/; test/integration/ is opt-in
```

## Key decisions

- **CDK, one stack per Environment.** Lightsail has only L1 constructs; wrap them in our own L3 constructs. Route 53 is global, so DNS lives in the same stack: no companion or cross-region stacks. Construct IDs and resource names derive from the forum id, so adding or removing a forum touches only that forum.
- **Engine plugins.** Every engine-specific behaviour (minimum RAM, blueprint, install and email-refresh scripts, TLS capability, option validation, seed operations) lives behind `EngineAdapter`. Core modules (`infra/`, `seeder/`, `metadata/`) must not import from `engines/discourse` or `engines/flarum`. Adding XenForo later means adding `engines/xenforo/` and one registry line.
- **Docker on the instance.** Discourse uses the official `discourse_docker` launcher. Flarum uses Docker Compose (PHP app, MySQL with a named volume, Caddy proxy). User data is generated by the adapter on top of a shared prelude and must be idempotent across reboots.
- **Instance credentials.** Lightsail instances cannot use instance profiles. Each instance registers as an SSM hybrid managed node using a single-use, 1-hour activation it claims from a per-Environment bootstrap broker, which only answers requests from that forum's static IP. Activation codes never appear in templates, user data or logs. Each forum's node role reads only `/community-hub/<env>/<forumId>/*`, writes only its API key, and (DNS-01 forums only) changes only its own `_acme-challenge` TXT record.
- **DNS in Route 53.** Modes: `route53` (Platform creates the public zone), `route53-existing` (operator zone, validated at synth with `HostedZone.fromLookup`, never managed as a resource), `external` (outputs only). Domain registration is out of scope.
- **TLS with Let's Encrypt on the instance.** A shared, pinned and checksum-verified `lego` issues and renews certificates on the host: DNS-01 through Route 53 in the Route 53 modes when the adapter supports it, HTTP-01 otherwise. The engine consumes the certificate files through adapter-declared paths and a reload command.
- **Email through Amazon SES only.** One domain identity per Environment (Easy DKIM, custom MAIL FROM, default configuration set, bounce/complaint SNS topic). Each forum gets an IAM user allowed only to send as its own sender address. A custom resource creates its access key, derives the SMTP password, and stores it as a SecureString; rotation is driven by `credentialRotation`.
- **Secrets by reference.** YAML only holds Secret_References. Values are resolved at runtime and never appear in templates, user data, logs or CLI output.
- **Snapshots.** Lightsail automatic snapshots daily; a lifecycle custom resource takes a manual final snapshot before an instance is deleted, so backups survive destroy.
- **Seeder as reconciler.** Read actual state, compute a plan with a pure function, then execute. Dry-run stops after planning. Unmanaged entities are never deleted.

## Boundaries to preserve

- No AWS SDK calls inside `seeder/reconciler.ts`, `metadata/`, or any pure builder (`node-role.ts`, `email/*-policy.ts`, `email/smtp-password.ts`, `email/email-dns-records.ts`, `dns/zone-check.ts`, `tls/*`, `user-data/tls.ts`). Side effects stay in Lambda handlers, seed clients, executors and `shared/`.
- `src/infra/` makes no SDK calls at synth. The only synth-time AWS read is CDK's built-in hosted-zone lookup.
- No forum HTTP calls from CDK code.
- No secret values in any `ValidatedModel` field. The model carries references; resolution happens at the edge. The `SesSmtpCredentials` handler is the only deploy-time code that holds a secret, in memory only.
